# BlendRL Workflow & Command Reference Guide

This document contains reference guides, CLI command syntax, plot style specifications, and workflow tutorials for the BlendRL repository.

---

## 1. Modular Plot Generation & Custom Styles
Visualizations are auto-generated by the modular framework in `plot/manager.py`, which reads CSV logs from `results/logs/[GROUP]/[EXP_ID]/[AGENT]/version_X/metrics.csv`.

### Modular Architecture (`plot/`)
- `plot/manager.py`: Entry-point orchestrator auto-dispatched by `run_pipeline.py`.
- `plot/base.py`: Base plotter providing hierarchical config merging (`_config.yaml` default < experiment YAML `plots` section < CLI args).
- `plot/convergence.py` (`_convergence_config.yaml`): Convergence curves (`eval/reward`, `train/reward`, `train/length`).
- `plot/losses.py` (`_losses_config.yaml`): Loss curves with per-metric filtering (`losses/actor_loss`, `losses/q_loss`, etc.).
- `plot/reports.py` (`_reports_config.yaml`): Markdown hyperparameter and method comparison tables.

### Plot Commands
```bash
# Auto-generate all plots requested in the experiment config
python3 plot/manager.py cp_final

# Run specific plotter standalone with CLI overrides
python3 plot/losses.py cp_final --metrics losses/q_loss losses/actor_loss --window 20

# Run convergence plotter standalone
python3 plot/convergence.py cp_final --window 15 --dpi 300
```

### Specifying Versions in Sources (`in/config/plot_sources/`)
In your sources YAML config, you can specify exactly which versions to plot using the `version` key. It supports integers, strings, or a list of versions to compare side-by-side:
```yaml
runs:
  - path: "results/logs/ungrouped/cp_final/ppo_cp_tuned"
    label: "PPO (v0 vs v1)"
    version: [0, 1]  # Load version_0 and version_1 of this method
  - path: "results/logs/ungrouped/cp_final/blendrl_cp_tuned"
    label: "BlendRL (Latest)"
    version: 3       # Load only version_3
```

### Style Configurations (`in/config/plot_styles/`)
You can define custom plotting formats in YAML files. Each entry in the `plots` list supports:
* `metric`: The exact column name in `metrics.csv` to plot (e.g., `eval/reward`, `losses/q_loss`).
* `split_by`: *(Optional)* Attribute to split runs into separate plot files (e.g., `source` to split by offline dataset source).
* `title`: The title template, supporting `{split_value}` and `{experiment}` placeholders.
* `filename`: Output filename template, supporting `{split_value}` and `{experiment}`.
* `window`: Rolling average window size for smoothing curves (e.g., `20`).
* `x_axis`: Column to map to the X-axis (`transitions` or `step` / `epoch`).
* `xlabel`: Legend name for the X-axis.

## 2. Adding Custom Methods & Architectures

### Adding a Custom Algorithm (Agent)
Algorithms are modular PyTorch Lightning Modules situated in `src/usr/algorithms/` (or installed as plugins). To implement a new algorithm:

1. **Create the Algorithm Script**: Create `src/usr/algorithms/my_new_algo/agent.py` subclassing `OfflineAgentBase`, `OnlineAgentBase`, or `lightning.LightningModule`. Ensure you implement:
    * `training_step(self, batch, batch_idx)`: Process transitions and return training loss.
    * `get_action_and_value(self, obs, logic_obs=None, action=None)`: Used during evaluation steps.
    * `configure_optimizers(self)`: Return your model's optimizers.
2. **Register the Algorithm**: Decorate your class with `@register_algorithm`:
    ```python
    from src.usr.algorithms.agent_registry import register_algorithm
    from src.usr.algorithms.base_agent import OfflineAgentBase

    @register_algorithm("my_new_algo")
    class MyNewAlgorithm(OfflineAgentBase):
        ...
    ```
3. **Define Hyperparameters**: Create a configuration file `in/config/agent/my_new_algo.yaml` to specify default parameters (e.g., learning rates, batch sizes).

### Adding a Custom Architecture
Neural architectures are instantiated via `get_neural_agent` in `src/utils.py`.
* **Vector Environments (MLP)**: If the environment config specifies `architecture: mlp`, the selection loader checks for the existence of `in/envs/[env_name]/mlp.py`. Place your customized neural network class (`MLP`) in that file. If it doesn't exist, it will fallback to the generic architecture.
* **Image Environments (CNN)**: Default CNN actors (`CNNActor`) are loaded automatically when no environment-specific architecture is provided.

## 3. Specifying Experiments (Hydra Configurations)

Experiments are structured hierarchically under `in/config/`:
* `in/config/config.yaml`: The base configuration file defining defaults, paths, and SLURM defaults.
* `in/config/agent/`, `in/config/env/`, `in/config/mode/`: Directory-specific defaults for algorithms, environments, and online/offline modes.
* `in/config/hydra/sweeper/`: Reusable Optuna sweeper templates (`optuna_offline.yaml`, `optuna_online.yaml`).
* `in/config/experiment/`: Group subdirectories (`cartpole/`, `mimic/`, `pyrenees/`, `cew/`, `tuning/`, `early_prediction/`, `quick_tests/`).

### Creating an Experiment Configuration
To specify a new run (e.g., `in/config/experiment/mimic/mimic_cql.yaml`):
1. Add `# @package _global_` at the top of the file.
2. Override configurations using the `defaults` section (offline defaults auto-set `total_timesteps: auto` and `save_dataset: false`):
    ```yaml
    # @package _global_
    defaults:
      - mimic/_base

    offline_methods: [cql/dnn]
    ```
3. Group defaults (`_base.yaml`), dataset resolution, and `experiment_id` are automatically handled.
4. **Override Experiment ID** (to prevent overwriting saved results across multiple runs of the same config template):
    ```bash
    python run_pipeline.py mimic_cql --exp-id mimic_run_2
    # Or shorthand alias:
    python run_pipeline.py cp_final -e cp_run_v2
    # Or Hydra override:
    python run_pipeline.py quick_test experiment_id=test_run_b
    ```
5. Validate your configuration before running:
    ```bash
    python run_pipeline.py mimic_cql --dry-run
    # Both shorthand 'mimic_cql' and path 'mimic/mimic_cql' work seamlessly!
    ```

### Hyperparameter Tuning with Optuna Sweepers
Tuning is an orchestration modifier defined declaratively inside any experiment under `methods:`. You can specify a shared search space under `methods.params.tune` and/or method-specific search spaces under `methods.<method_name>.tune`. 

**Example Tuning Experiment (`in/config/experiment/mimic/cql_tune.yaml`):**
```yaml
# @package _global_
defaults:
  - mimic/_base

tuning:
  n_trials: 40

methods:
  params:
    tune:
      lr: interval(1e-4, 1e-2)

  cql_dnn:
    agent: cql
    model: dnn
    tune:
      cql_alpha: choice(0.1, 1.0, 5.0)
```
When `tune:` is present (or `--multirun` is passed), the pipeline automatically activates Optuna, runs the trials, promotes the winning trial's checkpoint to `best_model.ckpt`, and saves `best_params.yaml`.

**Zero-Overhead Default**: If no `tune:` block is defined, the pipeline trains a single normal model directly without any sweeper or multirun overhead.

**Downstream Evaluation with `from_study`**:
Subsequent benchmark or evaluation experiments can load winning hyperparameters automatically:
```yaml
# @package _global_
defaults:
  - mimic/_base

methods:
  cql_dnn:
    agent: cql
    model: dnn
    from_study: mimic/cql_tune  # Automatically loads best_params.yaml into agent/model parameters
```

## 4. Workflow: Local Dev & Cluster Pipeline

To optimize efficiency and avoid wasting compute resources on cluster runs, follow this step-by-step workflow:

### Step 1: Local Sanity Check (Getting Methods Healthy)
Before pushing code or running sweeps, validate that the training methods, callbacks, logging, and dataset-saving loops work correctly using a low-footprint local run:
```bash
python run_pipeline.py cp_final total_timesteps=1000 eval_episodes=5 local=true save_dataset=false
```

### Step 2: Local Hyperparameter Sweeping (Optuna)
Once the method is healthy, perform a local hyperparameter search using the Hydra Optuna sweeper:
```bash
python run_pipeline.py quick_test -m agent.lr="interval(1e-4, 1e-2)" agent.tau="interval(0.5, 0.9)"
```

### Step 3: Cluster Deployment & Remote Execution
Once verified locally:
1. **GitHub Push Mandate**: Whenever suggesting or executing a command to run on the cluster (e.g., `local=false` or Slurm batch jobs), the agent MUST commit and push all recent code changes, configs, and scripts to GitHub first so that the remote repository is ready to be pulled and executed on the cluster.
2. Submit your runs to the Slurm scheduler by setting `local=false` (e.g. `python run_pipeline.py cp_final local=false`).
3. After execution finishes on the cluster, sync the `results/logs/` and `results/checkpoints/` directories back to your local machine for analysis and plotting.
